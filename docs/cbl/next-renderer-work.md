## Deferred intro recording analysis

The MP4 in `target/diag/examples/screenshots/Recording 2026-11-25 151450.mp4` contains 719 H.264 samples at a constant 30 FPS, about 24 seconds of video, and an AAC track. I inspected the container timing. Frame pixels and audio playback could not be inspected in this environment. The encoder's regular sample times allow repeated or unevenly updated source images, so the file timing alone cannot tell us where the visible hitch occurred.

The likely matching log is `target/diag/examples/rtx5080-20261125-151421-376/boot.log`. The recording filename is the approximate time anchor. Around 15:14:48–15:14:58 Sydney time, summaries show 29.9–30.0 FPS, 6–14 draws/frame, roughly 1–2% GPU busy by VIctory's queue estimate, and zero reported pipeline drops. A 14.6 FPS sample at 15:14:32 predates the filename timestamp. The log shows a warm library, and a pipeline batch near 15:14:52 reports zero newly made and 2,180 loaded. This puts sustained GPU load and cold shader compilation lower on the list for the recorded interval. A brief CPU stall or contention while loading pipelines is still possible.

The likely causes are uneven delivery from the movie path, uneven host presentation or capture cadence, and repeated or stale image content. The game loads Bink in this session, but that fact alone does not identify the decoder or path used by the recorded shot. [The other intro issue](https://github.com/fxceless/victory-fork/issues/103) concerns failure to play on a different machine.

## Implementation notes

Items 1–3 cover the deferred intro. Items 4–5 cover the current geometry work.

1. **Instrument the intro boundary.** Reuse the existing `victory_gpu::frame` debug target. Record the title frame ID and monotonic time at [queue present entry](../../crates/victory-gpu/src/queue.rs), then measure the host copy/submit and the DXGI present call separately in [host.rs](../../crates/victory-gpu/src/host.rs). The existing meter counts after `Present(0, ...)` even when it returns an error. Record the result and whether a usable title plane reached the host. Keep these as opt-in diagnostic events and preserve the current timing, return behavior and sync interval in the first patch.
2. **Run the intro twice with the same warm caches and display settings.** Capture one run without screen recording and one with it. Use PresentMon outside the renderer to record displayed intervals and drops, and record the monitor refresh rate. Launch the diag executable directly for a targeted trace using `VICTORY_LOG=warn,victory_gpu::frame=debug`. The default script sets the level to info. Align the trace, PresentMon rows and clip by elapsed time. Compare median, p95, p99 and count gaps above 50 ms for the same intro segment. [PresentMon CSV implementation](https://github.com/GameTechDev/PresentMon/blob/main/PresentMon/PresentMon/CsvOutput.cpp)
3. **Apply the fix at the first boundary with bad timing or repeated content.** Gaps before queue present point to the title feed, storage or CPU scheduling. Measure relevant movie frame delivery and waits before touching clocks. Regular calls with host copy stalls point to submission or the diagnostic black-frame probe, which allocates a readback on the synchronous path for supported formats. Add an opt-in probe A/B if that path shows up in the trace. Regular submission with uneven displayed intervals points to swap chain and desktop pacing. Regular intervals with repeated content call for a short frame-content comparison and a check of video texture updates. If the repeated images occur only in the recording, focus on the recorder. The acceptance check is a repeatable reduction in visible gaps with audio still in sync and the menu transition intact.
4. **Build a targeted geometry capture for the cashier and existing prison save.** Start with the existing capture files and a reproducible camera. If the operation dump cannot tie a missing surface to its output, extend [capture.rs](../../crates/victory-gpu/src/capture.rs) and [draw.rs](../../crates/victory-gpu/src/draw.rs) for one selected frame. Record color/depth target IDs, draw or dispatch shader hashes, indirect counts, and the reason a relevant draw or view was dropped or replaced with null. Keep this scoped to selected frames and targets. Examine one wall or ceiling edge beside a known-good prop. A depth hole sends the investigation to mesh submission, culling and descriptors. Intact depth sends it to material and composition. Compare scene color with the final image to localize the bloom, blur and fringing.
5. **Write one renderer fix from that capture.** Both local logs report a 1,245,184-view request capped at 1,000,000 views. Earlier samples had zero *dynamic table* refusals, which is a separate counter. If a required indexed view resolves to the null cap, identify the exact consuming shader before changing mapping or allocation. If depth is present, identify the first incorrect lighting or composition output, then fix the corresponding resource view, shader translation or pass. In the cashier log, `f133e35efed2a48a` fails translation on a lane-mask exchange and four compute PSOs are refused in late samples. Trace their bindings and outputs before choosing one. The completion check is a previously wrong surface that renders across a camera turn and reload, with evidence of which pass changed.
